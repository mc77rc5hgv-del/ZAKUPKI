# Архитектура проекта

Проект разделён на слои. Зависимости направлены снаружи внутрь: интерфейсы используют сценарии и инфраструктуру, инфраструктура использует доменные типы, а домен не зависит от Telegram, MCP, Playwright или OpenAI.

```text
src/
├── domain/                 # Чистые бизнес-правила закупок
│   └── procurement.ts      # Tender, TenderFilter, нормализация, фильтрация, скоринг
├── application/            # Прикладные порты и сценарии
│   └── mcp-client.ts       # Типизированный вызов инструментов MCP
├── infrastructure/         # Внешние технологии
│   ├── ai/                 # OpenAI-анализ
│   ├── persistence/        # Файловое хранилище пользователей
│   └── rts/                # Playwright, сессия РТС, извлечение DOM
├── interfaces/             # Входящие интерфейсы
│   ├── mcp/                # MCP tools и stdio server
│   └── telegram/           # Telegram UI, команды, фильтры и мониторинг
├── config/                 # Конфигурация процессов
└── entrypoints/            # Минимальные composition roots
    ├── mcp.ts
    └── telegram.ts
```

## Правила зависимостей

1. `domain` импортирует только стандартную библиотеку или ничего.
2. `application` может импортировать `domain`, но не Telegram/Playwright.
3. `infrastructure` реализует технические детали и может использовать `domain`.
4. `interfaces` собирает пользовательские сценарии, но не содержит парсинг HTML или бизнес-формулы.
5. `entrypoints` только запускают готовый интерфейс.
6. Секреты читаются из окружения; в исходный код и Git они не попадают.

## Как добавлять функциональность

### Новый фильтр закупок

1. Добавить поле в `TenderFilter`.
2. Реализовать правило в `filterTenders`.
3. Добавить Zod-поле в `rts_search_advanced`.
4. Добавить Telegram-алиас в `interfaces/telegram/filters.ts`.
5. Добавить unit-тест в `tests/procurement.mjs`.

### Новый раздел или действие РТС

1. Навигацию и DOM-извлечение разместить в `infrastructure/rts`.
2. Создать семантический MCP-инструмент в `interfaces/mcp`.
3. Для изменяющего действия использовать `RTS_ALLOW_WRITES` и явное подтверждение.
4. Добавить Telegram-команду только после появления стабильного MCP-контракта.
5. Не передавать пароль, CAPTCHA, PIN или закрытый ключ через MCP/Telegram.

### Новое хранилище

Текущая JSON-реализация находится в `infrastructure/persistence`. При переходе на PostgreSQL интерфейс данных следует вынести в `application`, а JSON и PostgreSQL сделать взаимозаменяемыми адаптерами.

### Новый канал интерфейса

Web/API-интерфейс добавляется рядом с Telegram в `interfaces/`. Он должен использовать существующие доменные правила и MCP-клиент, а не копировать фильтрацию.

## Границы безопасности

- чтение и аналитика могут выполняться автоматически;
- действия, меняющие состояние площадки, выключены по умолчанию;
- подписание ЭП и финальная отправка всегда требуют человека;
- URL ограничиваются origin площадки;
- пользовательские Telegram ID задаются allowlist-переменной;
- `.env`, профили браузера, загрузки и данные бота исключены из Git.

## Дальнейшее разбиение

При росте кода следующими самостоятельными модулями должны стать:

- `domain/procurement/normalization.ts`;
- `domain/procurement/filtering.ts`;
- `interfaces/mcp/tools/*` — один файл на группу инструментов;
- `interfaces/telegram/handlers/*` — команды, callbacks, pipeline, filters;
- `application/ports/*` — контракты репозиториев и клиента площадки.

Разбивать модуль стоит, когда он получает отдельную причину для изменения или превышает примерно 300–400 строк.
